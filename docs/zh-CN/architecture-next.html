下一版架构边界 ​

本文记录下一版 VILab 架构的目标边界，用于指导后续服务端、Web 管理端、桌面端和 SDK 的改造。它描述的是目标方向，不等同于当前已经完全落地的实现。

下一阶段先收敛到一个核心能力：语音输入到文本输出。语音服务能力负责 ASR 和 LLM 处理，客户端只负责采集音频、展示结果或把结果插入到本机输入位置。

核心结论 ​

  • 语音服务能力有两种承载形态：独立 VILab Server，以及桌面端内嵌本地服务。
  • Web 管理端是独立 VILab Server 的配置入口，只给管理员使用。
  • 桌面端可以完全使用自己的内嵌本地服务，不依赖独立 VILab Server。
  • 桌面端负责录音、快捷键、文本插入，并调用本地或远程语音服务。
  • SDK 只作为 WebSocket 流式语音客户端。
  • 本阶段不做 pipeline 暴露。
  • 本阶段不做用户级模型隔离。
  • 本阶段不提供 HTTP 非流式转写能力。

服务能力形态 ​

下一版架构不是只有一个远程服务端。VILab 的语音能力可以由两种形态承载：

形态运行位置典型使用方式配置入口
独立 VILab Server服务器、Docker、云主机、局域网主机多客户端共享、Web 管理、SDK 接入Web 管理端
桌面端内嵌本地服务用户自己的 Windows 或 macOS 设备单机使用、离线或本机模型、本地文本插入桌面端本地设置

独立 VILab Server 和桌面端内嵌本地服务都可以提供“语音输入到文本输出”的能力。区别在于：独立服务端面向多客户端共享和集中配置；桌面端内嵌本地服务面向单机体验，可以完全不连接独立 VILab Server。

独立服务端职责 ​

独立 VILab Server 只对外提供语音输入到文本输出相关能力。

独立服务端负责：

  • 接收实时音频输入。
  • 调用当前全局 ASR 配置，返回 ASR 中间结果和最终结果。
  • 调用当前全局 LLM 配置，返回 LLM 流式结果和最终结果。
  • 聚合一次语音会话的最终输出。
  • 保存和读取全局 ASR、LLM、Prompt 等服务配置。
  • 提供 Web 管理端需要的管理接口。
  • 提供 WebSocket 实时语音协议。

独立服务端不负责：

  • 桌面窗口、托盘、系统快捷键。
  • 本机麦克风选择。
  • 文本插入、剪贴板、输入法桥接。
  • 每个普通用户自己的模型偏好。
  • SDK 本地模型配置。
  • 客户端侧 UI 交互状态。

当前阶段的独立服务端配置是全局配置。管理员在 Web 管理端切换 ASR 或 LLM 后，所有连接到该独立服务端的桌面端、Web 使用端和 SDK 调用方都会使用新的全局配置。

Web 管理端职责 ​

Web 管理端只给管理员使用，普通内测用户不会拿到管理地址。它管理的是独立 VILab Server 的全局配置，不管理用户本机桌面端的内嵌本地服务。

Web 管理端负责：

  • 配置全局 ASR Provider、URL、Key 和模型名。
  • 配置全局 LLM Provider、URL、Key 和模型名。
  • 配置全局 Prompt 或文本后处理策略。
  • 测试 ASR、LLM 和完整语音链路。
  • 查看服务端运行状态。

Web 管理端不面向普通用户提供模型切换能力。普通用户只使用语音能力，不修改服务端配置。

权限模型在当前内测阶段保持简单。可以先使用固定管理员入口、固定账号密码、固定 token，或者仅在受控内网环境暴露管理端。完整账号体系、数据库用户表、细粒度权限和多租户隔离不属于本阶段目标。

桌面端职责 ​

桌面端是本机用户体验入口，同时保留自己的内嵌本地服务。桌面端可以完全使用本地服务完成 ASR、LLM 和文本插入，也可以连接独立 VILab Server 使用远程语音服务。

桌面端负责：

  • 录音。
  • 全局快捷键。
  • 显示录音和转写状态。
  • 调用本机内嵌服务或独立 VILab Server 的 WebSocket 实时语音接口。
  • 接收 ASR 和 LLM 的流式事件。
  • 把最终文本插入到当前应用的光标位置。
  • 在插入失败时提供复制、重试或错误提示。

文本插入是桌面端特有能力。服务端只返回文本，不操作用户本机。桌面端收到最终文本后，可以通过粘贴、模拟输入或输入法桥接把文本写入微信、飞书、浏览器、VS Code 等当前前台应用。

输入法端边界 ​

输入法端是桌面端的本机 OS 输入前端。Windows 输入法和 macOS 输入法继续保留当前设计：输入法进程读取桌面客户端生成的 ime-bridge.json，调用桌面客户端内嵌本地服务的 /admin/ime/* 接口，由桌面客户端完成录音、ASR 和 LLM 后处理，再由输入法端把最终文本写回当前输入框。

当前阶段输入法端不直接连接独立 VILab Server，也不管理 ASR、LLM、Provider Key 或服务端模型。后续如果需要接入独立服务端能力，也应优先保持“输入法端 -> 桌面客户端本地服务 -> 独立 VILab Server”的桥接路径，让输入法端继续只负责本机输入和文本写回。

桌面端连接独立 VILab Server 时，不负责：

  • 管理 ASR Provider。
  • 管理 LLM Provider。
  • 保存 Provider API Key。
  • 选择服务端模型。
  • 修改独立服务端全局配置。
  • 直接连接 LLM 做后处理。

桌面端使用内嵌本地服务时，可以继续保留当前桌面端已有的本地配置能力。这是桌面端单机路径，不等同于修改独立 VILab Server，也不会影响其他用户。

SDK 职责 ​

SDK 是 VILab 语音服务的实时客户端。它可以连接独立 VILab Server，也可以连接桌面端暴露的本机服务地址。

SDK 保留：

  • 连接 VILab 语音服务地址。
  • 建立 WebSocket 实时语音会话。
  • 发送音频流。
  • 接收 ASR 中间结果。
  • 接收 ASR 最终结果。
  • 接收 LLM 流式结果。
  • 接收 LLM 最终结果。
  • 接收 session 完成事件和错误事件。

SDK 移除或不再扩展：

  • HTTP 非流式转写。
  • pipeline 选择。
  • SDK-local LLM config。
  • models.add/update/delete/use 这类本地模型管理。
  • mode.set(local/remote) 这类客户端模式切换。
  • SDK 直连 LLM。
  • Provider Key 管理。
  • Admin API 调用。

新 SDK 的职责不是“管理 VILab”，而是“消费 VILab 语音服务的实时语音能力”。

本阶段不做 pipeline ​

下一阶段不向客户端暴露 raw、smart_clean、polish 等 pipeline。

服务端内部可以仍然有处理阶段，但客户端不选择 pipeline。一次语音会话默认执行固定链路：

text
音频输入
  -> ASR 中间结果
  -> ASR 最终结果
  -> LLM 流式结果
  -> LLM 最终结果
  -> 会话最终文本

如果后续需要支持“只 ASR 不润色”或“不同处理策略”，应先重新讨论协议，不在本阶段提前设计复杂 pipeline。

本阶段不做用户隔离 ​

当前内测阶段不做 per-user routing，也不做 per-key 模型隔离。

这意味着：

  • 独立服务端只有一套全局 ASR 配置。
  • 独立服务端只有一套全局 LLM 配置。
  • 管理员切换独立服务端模型会影响所有连接到该服务端的调用方。
  • 普通用户不能修改模型。
  • SDK 不能为某个用户单独切换独立服务端模型。

桌面端内嵌本地服务的配置只作用于本机桌面端，不属于独立服务端的用户隔离问题。

如果未来要支持多用户、多租户或不同项目使用不同模型，需要新增独立的用户、项目、权限和 routing 设计。当前文档不提前承诺这部分能力。

实时语音链路 ​

目标链路如下：

text
Desktop / Web 使用端 / SDK
  -> WebSocket
  -> 独立 VILab Server 或桌面端内嵌本地服务
  -> ASR Provider 或服务端本地 ASR Worker
  -> LLM Provider
  -> WebSocket events
  -> Client 展示或插入最终文本

服务端事件至少需要表达：

  • 会话已开始。
  • ASR 中间结果。
  • ASR 最终结果。
  • LLM 流式增量。
  • LLM 最终结果。
  • 会话完成。
  • 错误。
  • 取消。

具体事件名、消息字段、音频格式、二进制帧规则和关闭语义由 WebSocket 协议文档单独定义。

文档拆分 ​

本文件只定义架构边界。后续还需要继续确定：

  • WebSocket 实时语音协议：WebSocket 实时语音协议。
  • 下一版 SDK 设计：SDK 新 API、事件类型和迁移策略。

实现改造应先对齐这三份文档，再拆分 PR 落地。
