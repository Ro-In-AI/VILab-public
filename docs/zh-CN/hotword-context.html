热词上下文 ​

VILab 的后处理 prompt 已经拆成两层：稳定的核心 prompt 和按需注入的热词上下文。

核心 prompt 只描述长期稳定的编辑契约，例如只输出最终文本、不要回答口述里的请求、保留数字/日期/路径/命令、上下文不明确时不要猜专名。具体的 ASR 错词示例不再硬编码在核心 prompt 里。

热词、常见错听词、项目词、产品词和专业词属于可维护数据。系统会根据当前输入文本选择少量相关项，再把它们作为 Relevant hotword context 附加到本次 polished 请求中。

处理流程 ​

  1. raw 保留原始识别结果。
  2. smart_clean 先走本地规则，清理低风险口头语、重复词和明显改口。
  3. polished 构造核心 prompt。
  4. 启用的用户词库会作为 glossary 追加到 prompt。
  5. 内置热词 profile 会根据当前输入召回相关候选，只在命中上下文时注入。
  6. Provider 根据核心 prompt、用户词库和热词上下文生成最终文本。

例如当前输入包含 TTT、节词、测试用力 且语境明显是测试驱动和 prompt 优化时，本次请求可能注入：

text
Relevant hotword context:
Use these candidate ASR repairs only when the surrounding meaning supports them. If unsure, keep the input wording.
- TTT -> TDD
- 节词 -> 提示词
- 测试用力 -> 测试用例

如果当前输入只是普通闲聊，这些热词不会出现在 prompt 中。

为什么这样设计 ​

  • 核心 prompt 更短、更稳定，避免随着热词增长变成一份隐形词库。
  • 热词可以被测试、评估、分类和后续迁移到用户词库或服务端策略。
  • Prompt Lab 和历史评估更容易定位问题：是核心编辑规则的问题，还是某个热词上下文被错误注入。
  • 不同场景可以逐步引入不同 profile，而不需要复制或分叉整份 prompt。

维护规则 ​

  • 新增具体错听词时，优先放到热词 profile 或用户词库，不要直接写进核心 prompt。
  • 高风险或多义项必须要求上下文 hint，例如某个词在普通语境和开发语境下都可能成立时，只有命中相关上下文才注入。
  • 每个热词规则都应该有测试，至少覆盖“命中时注入”和“不相关时不注入”。
  • 注入内容应保持少量、直接、可解释；不要把完整热词库塞进单次请求。

相关代码 ​

  • 内置热词 profile：src-tauri/src/domain/builtin_hotwords.rs
  • Prompt 构造入口：build_transform_instructions_for_provider_with_context
  • Prompt 版本：vilab-dictation-polish-v15、ime-polished-v11

powershell
node scripts/with-libclang.mjs cargo test domain::text::tests:: --manifest-path src-tauri/Cargo.toml
