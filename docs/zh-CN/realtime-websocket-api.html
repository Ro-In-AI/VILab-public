WebSocket 实时语音协议 ​

本文定义下一版 VILab 实时语音协议 V1。它面向桌面端、Web 使用端和 SDK，目标是用同一套 WebSocket 协议完成“语音输入到文本输出”。

本文描述的是目标协议，不等同于当前 HTTP Public API 的现状。当前 HTTP API 仍使用整段 audio/wav 上传；WebSocket V1 使用流式 PCM 音频帧。

目标 ​

V1 只做一个能力：实时语音会话。

服务端负责：

  • 接收客户端实时音频。
  • 使用当前服务端配置进行 ASR。
  • 返回 ASR 中间结果和最终结果。
  • 使用当前服务端配置进行 LLM 文本后处理。
  • 返回 LLM 流式结果和最终结果。
  • 聚合并返回本次会话最终文本。

客户端负责：

  • 采集麦克风音频。
  • 按协议格式发送音频帧。
  • 展示 ASR 和 LLM 流式事件。
  • 在桌面端把最终文本插入本机当前输入位置。

非目标 ​

V1 不做：

  • pipeline 暴露。
  • HTTP 非流式转写。
  • 客户端选择 ASR 或 LLM 模型。
  • SDK 管理 Provider Key。
  • SDK 本地 LLM 配置。
  • 输入法 /admin/ime/* 协议替换。
  • 一个 WebSocket 连接承载多个并发会话。

协议分层 ​

一次实时语音会话会同时涉及几层协议。实现时应明确每一层只承担自己的职责。

层级使用协议或格式作用
传输层TCP + TLS负责可靠传输和加密。生产环境使用 TLS。
连接层HTTP WebSocket Upgrade客户端发起 WebSocket 握手，服务端接受后升级为双向连接。
鉴权层Header、Cookie 或短期 token在握手阶段完成鉴权，不在每条业务消息里重复传 key。
控制层WebSocket text frame + JSON发送 session.start、audio.end、session.cancel 和服务端事件。
音频层WebSocket binary frame + pcm_s16le承载实时音频数据。
关闭层WebSocket close frame表达正常完成、取消、协议错误或服务端错误后的连接关闭。

开发和本机调试可以使用 ws://127.0.0.1:<port>。生产、局域网跨设备或公网部署必须使用 wss://。

V1 固定规则 ​

V1 先固定以下对接规则，客户端和服务端都按这些规则实现。

  • WebSocket 路径固定为 /v1/realtime/sessions。
  • 一个 WebSocket 连接只承载一次语音会话。
  • 客户端必须先发送 session.start，并收到 session.started 后，才能发送 binary audio frame。
  • 客户端第一版按边录音边发送实现，不采用录完后再回放音频块作为默认路径。
  • JSON text frame 使用 UTF-8。
  • JSON 字段名固定使用 camelCase，例如 sessionId、elapsedMs、timeToFirstTokenMs。
  • V1 音频格式只支持 pcm_s16le / 16000Hz / mono。
  • 单个 binary audio frame 最大 32000 bytes，也就是最多 1 秒音频。
  • 推荐客户端每 100ms 发送一帧音频，服务端应接受 20ms 到 250ms 的常规帧大小。
  • 单次会话最大音频时长为 5 分钟。超过后服务端返回 audio_duration_exceeded fatal error 并关闭连接。
  • 客户端不能依赖 asr.partial。服务端 V1 可以只发送 asr.final。
  • 没有 LLM 后处理时，服务端不发送 llm.delta 和 llm.final，session.completed.finalText 等于 rawText。
  • fatal error 后，服务端先发送 error 事件，再发送 WebSocket close frame。
  • 客户端应优先读取最后一个 error 事件，不应只依赖 close reason。

连接流程 ​

推荐入口：

text
GET /v1/realtime/sessions

客户端通过 WebSocket 连接该地址。V1 规则是：一个 WebSocket 连接只承载一次语音会话。会话完成、取消或出现 fatal error 后，连接可以关闭。

完整流程如下：

text
1. WebSocket 握手
   client -> server: HTTP GET /v1/realtime/sessions + Upgrade: websocket
   server -> client: 101 Switching Protocols

2. 会话初始化
   client -> server: JSON text frame, type=session.start
   server -> client: JSON text frame, type=session.started

3. 音频上行
   client -> server: binary frame, pcm_s16le audio
   client -> server: binary frame, pcm_s16le audio
   client -> server: binary frame, pcm_s16le audio

4. 录音结束
   client -> server: JSON text frame, type=audio.end

5. 结果下行
   server -> client: JSON text frame, type=asr.partial  可选
   server -> client: JSON text frame, type=asr.final
   server -> client: JSON text frame, type=llm.delta    可选
   server -> client: JSON text frame, type=llm.final    可选
   server -> client: JSON text frame, type=session.completed

6. 连接关闭
   server 或 client -> peer: WebSocket close frame

1. 握手协议 ​

客户端先发起 WebSocket 握手。本质上这是一次 HTTP 请求，成功后升级为 WebSocket 连接。

示例：

http
GET /v1/realtime/sessions HTTP/1.1
Host: api.example.com
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Key: ...
Sec-WebSocket-Version: 13
Authorization: Bearer <token>

服务端接受后返回：

http
HTTP/1.1 101 Switching Protocols
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Accept: ...

鉴权策略由部署阶段决定：

  • 内测阶段先做协议字段校验：请求必须携带鉴权字段，但服务端暂不校验 token 内容。
  • 桌面端、服务端 SDK、CLI 等非浏览器客户端在握手请求里使用 Authorization: Bearer <token>。
  • 浏览器 WebSocket API 通常不能直接设置自定义 Authorization header，因此 Web 使用端使用短期 query token：/v1/realtime/sessions?token=<token>。
  • 后续正式版本可以在不改变协议字段的前提下，把“字段存在校验”升级为真实 token 校验。

鉴权发生在 WebSocket 握手阶段。业务 JSON 消息里不重复携带 API key。

内测实现规则：

  • 非浏览器客户端请求中存在 Authorization: Bearer <value> 即可通过。
  • 浏览器客户端请求中存在 token query 参数即可通过。
  • 空字符串、缺失字段或明显不符合 Bearer 格式的请求应拒绝。
  • token 内容的真实校验留到正式鉴权阶段实现。

2. 会话初始化协议 ​

握手成功后，客户端必须先发送一次 session.start JSON text frame。服务端收到后创建会话、固定配置快照，并返回 session.started。

在收到 session.started 之前，客户端不应发送 binary audio frame。服务端收到提前发送的 binary frame 应返回 audio_before_session_start 错误。

3. 音频上行协议 ​

session.started 之后，客户端连续发送 WebSocket binary frame。binary frame 只承载 PCM 音频，不再附带 JSON 元数据。

音频格式由 session.start.audio 声明。V1 只接受 pcm_s16le / 16000Hz / mono。如果客户端声明其它格式，服务端应在 session.start 阶段返回 invalid_audio_format。

4. 结束与取消协议 ​

客户端正常停止录音时发送 audio.end。服务端收到后停止接收新音频，完成 ASR 和 LLM 后处理。

客户端主动取消时发送 session.cancel。服务端应尽快停止当前会话并返回 session.cancelled，随后可以关闭连接。

5. 结果下行协议 ​

服务端通过 JSON text frame 返回事件。事件按阶段输出：ASR 中间结果、ASR 最终结果、LLM 流式增量、LLM 最终结果、会话完成。

V1 协议保留 asr.partial，但实现可以先只发送 asr.final。客户端必须能处理没有 asr.partial 的情况。

6. 关闭协议 ​

正常完成后，服务端可以在发送 session.completed 后关闭连接，也可以等待客户端关闭。推荐服务端主动关闭，避免连接长期空闲。

建议关闭码：

关闭码场景
1000正常完成或客户端正常关闭。
1002协议错误，例如未发送 session.start 就发送音频。
1003不支持的数据类型或音频格式。
1008鉴权失败或策略拒绝。
1011服务端内部错误、ASR/LLM 不可用。

音频格式 ​

V1 只支持一种音频格式：

json
{
  "encoding": "pcm_s16le",
  "sampleRate": 16000,
  "channels": 1
}

含义：

  • pcm_s16le：signed 16-bit little-endian PCM。
  • sampleRate：16000 Hz。
  • channels：1，单声道。

这是当前桌面客户端 STT 前已经使用的标准化格式。桌面端采集到设备原始音频后，会转成 i16 PCM，再统一处理为 16kHz、mono、i16 PCM。WebSocket 直接复用这个格式，不再为每个音频块包 WAV header。

二进制音频帧规则：

  • WebSocket binary frame 内容就是连续的 pcm_s16le samples。
  • 每个 sample 2 字节，小端序。
  • 推荐每帧 100ms，即 1600 samples，3200 bytes。
  • 服务端应接受 20ms 到 250ms 的帧大小。
  • 单个 binary frame 不应超过 1 秒音频，即 32000 bytes。
  • 单次会话累计音频不应超过 5 分钟，即 300 秒。超过后服务端应返回 audio_duration_exceeded fatal error。

HTTP 整段上传路径可以继续使用 audio/wav，但 WebSocket V1 不使用 WAV 作为流式帧格式。

客户端消息 ​

客户端消息分为 JSON text frame 和 binary audio frame。

session.start ​

session.start 是客户端连接后发送的第一条 JSON text frame。它只发送一次，用于声明本次会话参数。

json
{
  "type": "session.start",
  "language": "zh-CN",
  "audio": {
    "encoding": "pcm_s16le",
    "sampleRate": 16000,
    "channels": 1
  },
  "textContext": {
    "beforeCursor": "",
    "selectedText": "",
    "afterCursor": "",
    "markedText": ""
  }
}

字段：

  • type：固定为 session.start。
  • language：可选，语言提示。为空时服务端按 auto 处理。
  • audio：必填，V1 必须是 pcm_s16le / 16000 / 1。
  • textContext：可选，当前文本框上下文。桌面端和输入法端可以提供；Web/SDK 可以省略。

textContext 与现有输入法上下文字段保持一致：

  • beforeCursor：光标前文本。
  • selectedText：当前选中文本。
  • afterCursor：光标后文本。
  • markedText：当前预编辑文本。

服务端应在收到 session.start 时创建会话，生成 sessionId，并固定本次会话使用的服务配置快照。

binary audio frame ​

session.started 之后，客户端可以持续发送 binary audio frame。

binary frame 不需要额外 JSON 包裹，不需要 chunk id，不需要 WAV header。服务端按 session.start.audio 声明的格式解释全部 binary frame。

audio.end ​

客户端停止录音后发送：

json
{
  "type": "audio.end"
}

服务端收到后不再等待新的音频帧，开始或继续完成 ASR 和 LLM 后处理。

session.cancel ​

客户端取消会话时发送：

json
{
  "type": "session.cancel",
  "reason": "user_cancelled"
}

服务端应尽快停止 ASR/LLM 工作，返回 session.cancelled 或直接关闭连接。

服务端事件 ​

服务端事件都是 JSON text frame。

session.started ​

json
{
  "type": "session.started",
  "sessionId": "5efdc6ee-8f9b-4b58-a4cf-d3ab2cbdf2d4",
  "audio": {
    "encoding": "pcm_s16le",
    "sampleRate": 16000,
    "channels": 1
  },
  "configVersion": "cfg-1710000000000"
}

configVersion 标识本次会话使用的服务端配置快照。

asr.partial ​

ASR 中间结果。V1 协议保留该事件，但实现可以先不发送。

json
{
  "type": "asr.partial",
  "sessionId": "5efdc6ee-8f9b-4b58-a4cf-d3ab2cbdf2d4",
  "text": "今天下午",
  "stability": 0.72,
  "elapsedMs": 1200
}

字段：

  • text：当前 ASR 中间文本。
  • stability：可选，0 到 1。没有稳定度能力时可以省略。
  • elapsedMs：从会话开始到当前事件的耗时。

asr.final ​

ASR 最终结果。

json
{
  "type": "asr.final",
  "sessionId": "5efdc6ee-8f9b-4b58-a4cf-d3ab2cbdf2d4",
  "text": "今天下午三点开会",
  "elapsedMs": 1800
}

llm.delta ​

LLM 后处理增量。没有启用 LLM 后处理时不会发送。

json
{
  "type": "llm.delta",
  "sessionId": "5efdc6ee-8f9b-4b58-a4cf-d3ab2cbdf2d4",
  "delta": "今天下午",
  "text": "今天下午",
  "elapsedMs": 2100,
  "timeToFirstTokenMs": 260
}

字段：

  • delta：本次新增文本。
  • text：当前累计文本。
  • timeToFirstTokenMs：可选，从开始 LLM 请求到首个 token 的耗时。

llm.final ​

LLM 后处理最终结果。

json
{
  "type": "llm.final",
  "sessionId": "5efdc6ee-8f9b-4b58-a4cf-d3ab2cbdf2d4",
  "text": "今天下午三点开会。",
  "elapsedMs": 2600,
  "timeToFirstTokenMs": 260
}

session.completed ​

本次会话完成。客户端应以 finalText 作为最终输出。

json
{
  "type": "session.completed",
  "sessionId": "5efdc6ee-8f9b-4b58-a4cf-d3ab2cbdf2d4",
  "rawText": "今天下午三点开会",
  "finalText": "今天下午三点开会。",
  "timings": {
    "asrMs": 1800,
    "llmMs": 800,
    "totalMs": 2700,
    "timeToFirstTokenMs": 260
  },
  "configVersion": "cfg-1710000000000"
}

如果没有启用 LLM 后处理，finalText 可以等于 rawText，llmMs 为 0。

session.cancelled ​

json
{
  "type": "session.cancelled",
  "sessionId": "5efdc6ee-8f9b-4b58-a4cf-d3ab2cbdf2d4",
  "reason": "user_cancelled"
}

error ​

json
{
  "type": "error",
  "sessionId": "5efdc6ee-8f9b-4b58-a4cf-d3ab2cbdf2d4",
  "code": "invalid_audio_format",
  "message": "V1 only supports pcm_s16le, 16000Hz, mono audio.",
  "stage": "session.start",
  "fatal": true
}

常见错误码：

  • unauthorized
  • invalid_message
  • invalid_audio_format
  • audio_before_session_start
  • audio_too_large
  • audio_duration_exceeded
  • asr_unavailable
  • asr_failed
  • llm_unavailable
  • llm_failed
  • session_cancelled
  • internal_error

fatal: true 表示服务端会结束本次会话。

配置热更新 ​

Web 管理端修改 ASR、LLM、Prompt 或服务路由后，服务端必须支持热更新，不要求重启进程。

V1 语义：

  • 新建 WebSocket 会话必须使用最新已提交配置。
  • 已经开始的 WebSocket 会话使用 session.start 时刻的配置快照。
  • 不在同一个会话中途切换 ASR 或 LLM Provider。
  • 服务端在 session.started 和 session.completed 中返回 configVersion，用于定位本次会话使用的配置。

这样可以同时满足两个目标：

  • 管理员在 Web 端修改配置后，新请求立即生效。
  • 已经进行中的语音会话不会因为模型或 Provider 中途切换而产生不一致结果。

如果需要让长连接客户端感知配置变化，服务端可以发送可选事件：

json
{
  "type": "config.updated",
  "configVersion": "cfg-1710000005000",
  "appliesTo": "next_session"
}

config.updated 不改变当前会话的配置，只提示客户端下一次会话会使用新配置。

V1 不要求必须实现 config.updated。最低要求是：Web 管理端提交新配置后，新建会话必须使用最新配置。

当前可复用实现事实 ​

可以直接复用的现有事实：

  • 桌面端采集后已经能得到 i16 PCM samples。
  • 桌面端 STT 前已经统一转成 16kHz、mono、i16 PCM。
  • HTTP Public API 已有 asr.final、postprocess.final、run.completed 这类阶段事件思路。
  • 输入法 bridge 已经验证过 LLM delta + final commit 的流式文本体验。

需要新增的实现：

  • 服务端 WebSocket route。
  • 客户端边录边发送 binary PCM frame。
  • 服务端按会话缓存音频或增量喂给 ASR。
  • 服务端把 ASR/LLM 进度转换成本文定义的事件。
  • Web 管理端配置更新后的运行时热加载和 configVersion 标识。
