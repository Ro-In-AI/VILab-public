Text Context for Dictation ​

VILab dictation can send a small snapshot of the focused text field to the rewrite pipeline. This works for IME dictation and for the desktop client's normal dictation path. The snapshot is captured when dictation starts, then reused for that recording session. The model uses it only to produce the text that should be inserted or used as a replacement.

Why It Exists ​

This is useful when the spoken input depends on the current text, for example:

  • the user says "replace this with pending review" while some text is selected
  • the user says "also add 429 here" inside an English retry-policy note
  • the user says "ask them to send that by Friday" after a field already names the missing report
  • the cursor is in the middle of a sentence and punctuation must fit both sides

Without the focused-field context, the rewrite model only sees the transcript. It has to guess what "this", "that", "here", or "also" refers to.

IME Bridge Shape ​

The IME bridge sends the context in the POST /admin/ime/dictation/stream request body:

json
{
  "scene": "auto",
  "language": "zh-CN",
  "hasTextTarget": true,
  "textContext": {
    "beforeCursor": "Retry policy:\n- retries on 5xx\n",
    "selectedText": "",
    "afterCursor": "\n- max backoff attempts: 3",
    "markedText": ""
  }
}

Fields:

  • beforeCursor: text immediately before the cursor, capped by the client
  • selectedText: current selected text, when the user is replacing text
  • afterCursor: text immediately after the cursor, capped by the client
  • markedText: active preedit/composition text, when available
  • hasTextTarget: whether the IME still has a real text target for direct commit

Empty context fields can be omitted. The desktop backend drops an entirely empty textContext.

IME Flow ​

  1. The user triggers dictation from an IME.
  2. The IME captures the focused text-field snapshot before recording starts.
  3. The IME calls /admin/ime/dictation/stream with textContext and hasTextTarget.
  4. The desktop app records audio, runs STT, then builds the rewrite prompt with the text context.
  5. The model returns only the final insertable text, not the whole field.
  6. The IME commits that returned text into the original target.

Desktop Client Flow ​

  1. The user triggers normal VILab client dictation without using the IME.
  2. The desktop app captures the focused text-field snapshot before starting native recording or showing the overlay.
  3. The app stores the snapshot with the recording session.
  4. When recording stops, the app uses that stored context to build the rewrite prompt.
  5. The final model output is inserted back into the original target when the target is still current.

Platform Notes ​

  • macOS captures the context through the IMK text input client at dictation start.
  • Windows captures the context through a synchronous TSF read edit session at dictation start. It reads selection, text before/after the selection, and the current composition range when available.
  • macOS desktop client dictation reads the focused text control through Accessibility APIs before recording starts.
  • Windows desktop client dictation reads the focused text control through UI Automation TextPattern/TextPattern2 before recording starts. It uses GetSelection for replacements and GetCaretRange for insertion context.
  • If a host application refuses to expose text, the field is missing. Dictation still works; the rewrite just has less context.
  • Password fields and protected controls should not expose useful text through normal platform APIs.
  • UI Automation coverage is best-effort. Older, elevated, or custom-drawn Windows controls may support insertion but still refuse to expose readable context.

Privacy And Retention ​

The context is deliberately small and session-scoped. Clients cap text around the cursor to 1,000 UTF-16 code units per side. The backend includes the context in debug diagnostics only for debug builds; release builds do not persist the field-context payload in recording diagnostics.
